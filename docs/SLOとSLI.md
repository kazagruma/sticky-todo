# 第66課題：信頼性を数字で決める

## 目標と指標

提案SLO：30日間の観測成功率99.5%以上。成功応答の95%以上が2秒以内。
SLI：成功回数÷実施した観測回数。成功条件は10秒以内にHTTP 200かつHTMLにSticky ToDoを含むこと。
応答時間は本文の取得完了まで。15分間隔での定点観測を想定する。
99.5%を時間で単純換算すると30日で216分の停止に相当するが、このサンプル指標から実停止時間は断定できない。
欠測は成功と扱わず、予定した観測との不足数を別途確認する。観測点の通信障害も失敗になる。
ページ到達性のみを対象とし、付箋の保存・AI・ユーザー操作の成功率は含まない。

## 実行・表示

プロジェクトで `node sli.mjs 3` を実行すると3回だけ本番を読み取り確認する。
`.sli-output/observations.jsonl` に追記し、直近30日の実施観測から `.sli-output/report.html` を生成する。
HTMLをブラウザで開くと目標・観測成功率・応答時間p95・最新ログ・対応ルールが見える。
このCLIは手動実行であり、定期スケジュールや通知は新設していない。
既存uptime.ymlは15分間隔だが、このCLIとは別の簡易HTTPチェック。月間SLIを自動集計しているわけではない。
定期運用には同じ成功条件の計測をスケジュールへ接続し、ログの永続化・欠測検知・通知到達確認を行う必要がある。

## 運用ルール

- 2回連続失敗：別回線・ブラウザで再確認し、監視側の問題とアプリ障害を切り分ける。
- 直近24時間の失敗率0.5%超、成功応答の5%超が2秒超：調査を開始する。
- Actions、Cloudflareの状態、直近デプロイを調べる。通知は既存Actionsの失敗通知設定と到達確認が必要。
- 直近変更が原因なら承認を得て既知の正常版へ戻す。原因不明のまま削除しない。
- 復旧後3回連続成功を確認し、時刻・影響・原因・再発防止を記録する。

設計判断：小規模な学習アプリでは99.5%から始め、実測を蓄積して目標を見直す。静的ページの到達性と利用者データの正常性を混同しない。
本番変更・push・NICOへの接続は実施しない。
