# ADR-0001：個人利用段階では端末内保存を維持する

日付：2026-10-20　状態：現行設計の追認（学習用記録）
対象：Sticky ToDoの付箋データ保存。AIへの許可済み送信は別の判断とする。

## 背景

現在は個人用の付箋管理。WebはlocalStorage、desktopはSQLite .tdfで保存している。ログイン・共有DB・端末間同期は未実装。現行の小規模運用に、将来の共有機能を見越した複雑さを今から持ち込むべきかを判断する。

## 検討した選択肢

|案|良い点|代わりに負うもの|
|---|---|---|
|A：端末内保存を維持|サーバーDB・認証が不要。個人データを中央に集めず、構成が小さい|自動同期・共有・中央バックアップがない。端末消失やブラウザ削除への備えが必要|
|B：認証＋共有API＋クラウドDB|複数端末・共同利用・中央バックアップを設計できる|認証・顧客分離・権限・移行・運用費・障害対応が増える|
|C：ローカル＋クラウド同期|ローカル操作と端末間利用を両立しやすい|競合解決・再送・重複防止・削除同期が難しく、実装と検証が最も重い|

## 決定と理由

**今はAを維持する。** BやCも検討したが、現段階の個人利用には共有要件がなく、認証・顧客分離・同期の追加コストが利益を上回るため。これは将来のクラウド化を禁止する決定ではない。

## 結果・制約

- Webのデータはブラウザ／オリジンごと、desktopは選択ファイルごと。両者の自動同期を期待させない。
- 端末内保存は暗号化や完全な安全性を意味しない。desktopの待ち保存等はWebview localStorageにも残る。
- バックアップは別途必要。Webのエクスポート／インポートは実装確認なしに保証しない。
- クラウド移行時は既存データの同意付き取込み、所有者ID、権限、削除・復元、ロールバックを設計する。

## 見直す条件

「スマホとPCで共有したい」「複数人で同じボードを使いたい」「管理者による復旧が必要」のいずれかが具体的な必須要件になった時。Bを第一候補に再比較し、オフライン必須ならCも評価する。新ADRで旧判断を置き換える。

設計判断の一言：**共有DBも選べたが、今は個人利用に必要な小ささを優先し、端末内保存を維持した。**
